## Lead 分解与 Coordinator 路由的当前流程

Lead 接收 question 和 enhanced_context，再把角色能力、尽量少分解、子任务应独立等要求作为 system prompt，调用 LLM 生成 subtasks 列表。每项主要包含 description 和 assigned_agent。当前不是确定性规则分类器，也不是直接选择工具；工具由 Worker 后续选择。

`swarm/lead_agent.py:198 assess_and_decompose()` 用正则提取 JSON，解析后直接返回。没有匹配到 JSON 时，默认分配 ConsultationAgent；解析或模型请求发生异常时返回空列表。解析成功不代表任务结构、语义或授权有效。

`swarm/swarm_coordinator.py:153` 按子任务数量路由：

- 1 项：按 assigned_agent 找 Worker，传原始 question、增强 context 和 session_id 执行；未知 Agent 回退 ConsultationAgent。该路径没有直接执行 Lead 的子任务 description。
- 至少 2 项且 enable_swarm=True：创建 SharedContext，Lead.create_subtasks 生成 UUID、任务类型及分配对象，Coordinator 启动 Worker；Worker 查找分给自己的子任务并执行。
- 0 项，或多任务但 enable_swarm=False：回退 ConsultationAgent。禁用多 Agent 仍会调用 Lead 分解。

分流条件是子任务数量，不是不同 Agent 数量。多个子任务分给同一个 Worker，也会进入 swarm 分支。所有 Worker 都被启动，有分配任务的才实际执行。因此“两个任务”不能直接解释为“两个不同专家参与”，也不能认为多任务必然应并行。

Swarm 是当前项目的多任务处理分支：创建共享任务/贡献容器、分配任务、并行运行、等待和汇总。`_worker_execute_assigned_tasks()` 对没有任务的 Worker 立即返回；对同一 Worker 的多个任务也会 create_task 并行处理。Worker 默认仅收到子任务 description、id 和 type，主链路没有自动读取其他 Worker 贡献或互相辩论。三个角色均产生有效结果后，可以描述为“多角色分工并汇总”；只有启动三个对象，或设置 swarm_enabled=True，不能证明三个角色完成，更不能证明比单 Agent 更好。

## 框架选型候选 暂不迁移

当前 medix-agent-swarm 的 Python 源码及依赖清单没有发现 LangChain/LangGraph 的使用。实现主要是 Python 类、OpenAI-compatible SDK、手写 AgentLoop、asyncio 并发、SharedContext 和内存 StateManager。Agent 行为由模型、工具、消息反馈和控制程序构成，不依赖某个指定框架才成立。

[LangChain 官方概述](https://docs.langchain.com/oss/python/langchain/overview) 提供高层 Agent 构建和模型/工具集成；[LangGraph 官方概述](https://docs.langchain.com/oss/python/langgraph/overview) 定位为状态化编排运行时，可混合确定性步骤与模型决策，提供持久化、人机交互和流式执行等基础能力，也可以不搭配 LangChain 使用。

| 编号 | 备选方案 | 适用与优势 | 代价与限制 | 状态 |
|---|---|---|---|---|
| ARCH-01A | 保留 Python + 显式 Workflow | 路径短、业务状态少时，依赖少，容易理解和做确定性测试 | 恢复、暂停、依赖调度和并发状态需要自己完善 | 候选，未实施 |
| ARCH-01B | LangGraph StateGraph 编排，保留可复用工具/Service；需要时使用 LangChain 模型或 Agent 组件 | 需要明确节点、条件路由、等待人工确认、多轮恢复和故障恢复时有价值 | 新依赖与状态/节点学习成本；持久 checkpointer、身份与工具副作用仍需设计 | 候选，未实施 |

可能的节点映射：输入与上下文 → Lead 规划 → 计划校验 → 条件路由 → 单 Worker 或并行分支 → 汇总 → 保存结果。现有 AgentLoop 可先作为 Worker 节点内部逻辑，不需要第一步整体重写。

LangGraph checkpoint 保存流程进度，关系数据库消息表保存完整聊天，Mem0 或本地长期记忆保存跨会话检索材料，三者用途不同。采用框架不自动修复错误分解、用户权限、人工确认绑定、幂等写入或跨用户隔离。持久恢复需配置持久存储，并对重放时的工具副作用单独设计。

最终选择在全项目理解完成后，按真实业务复杂度、既有技术栈、恢复要求和离线测试成本比较，不以“主流”代替需求判断。本阶段不安装依赖、不迁移、不接入 LangSmith 等云跟踪服务。

从面试表达角度，LangGraph 可以用状态、节点、条件边和 checkpoint 清晰说明流程；但“框架更熟悉”不能作为实现更可靠或招聘认可度必然更高的证据。若后续选用，应展示具体解决的暂停确认、依赖执行或失败恢复问题，以及可复现测试。Python 自实现保留为可比较基线，不将当前第三方工程当个人成果，也不在未迁移时声称已使用 LangGraph。

### 候选一 升级参考项目的查询分析链路

1. 接收请求与可信身份，生成 request/run 标识。
2. 按用户和会话加载近期消息，按授权范围检索相关历史；冻结本轮上下文快照。
3. 意图路由：明确简单解释/单项检索直接进入对应执行节点；不明确则追问；确需多个独立能力才调用规划节点。
4. 规划校验：验证结构、角色/工具允许范围、原问题覆盖、重复任务、依赖关系、任务数/时间/调用预算。
5. 按计划执行：一个能力用一个 Worker；独立只读任务可受限并行；依赖任务按顺序。所有 Worker 收到原问题、相关背景和具体子任务；结果按 task_id 合并，运行计数局部化。
6. 证据检查：检查来源标识、缺失结果、任务失败与冲突；类型和权限由程序检查，内容复核可用可选模型辅助，不能把它当绝对正确性保证。
7. 对可修复缺口只做预算内的定向补查；仍无法解决时返回 partial/insufficient_evidence 或请求澄清，不为得到一致结论无限循环。
8. 有效结果汇总，最终检查返回状态与证据引用。单节点结果已经满足回答契约时，可避免额外模型汇总调用。
9. 保存用户对话、执行记录及按策略筛选的长期记忆，向前端返回 completed/completed_with_fallback/partial/failed 等明确状态和说明。

Reviewer 仅在确需内容复核时启用；不强制增加一个 Agent 或三方辩论。复核应围绕原始来源、字段矛盾、遗漏与权限，而不是多数票或文本意见一致。来源未能核实时保持缺口状态。

## 原项目 AgentLoop 按执行顺序拆解

核对日期：2026-10-13。依据 `core/agent_loop.py`、`core/state_manager.py`、`agents/base_agent.py` 和三个 Worker 的初始化配置。用户提供的手册 `D:/edge_download/居丽叶的简历项目7：医疗助手Agent.pdf` 共 43 页，已提取文字并渲染查看第 9 页；该页说明 ReAct 和 Loop，作为讲解参考，不能当作真实运行记录。原项目模型、工具和测试未执行。

AgentLoop 是单个 Worker 完成任务的循环引擎，Lead 规划和 Coordinator 路由在其外部。三个 Worker 共用该引擎实现；多 Agent 分支是在外层并行启动各自的执行流程，不是 Loop 内部固定轮流调用三个专家。

1. **准备本次运行**：创建内部 task_id 和状态，拼接角色提示、当前输入，以及有短期记忆且传入 session_id 时的近期消息；取得可用工具的名称、说明和参数结构。该内部 task_id 不等同于 SharedContext 的 subtask_id。
2. **请求模型决策**：把消息和工具说明发给模型，允许模型直接回答，或返回 tool_calls。模型输出的是工具调用请求，并不直接运行 Python；源码也没有要求单独输出一段可见的 Think 文本。
3. **由程序执行工具**：解析调用名称和参数，经 Agent/注册表找到已注册的函数并执行。同一模型响应中的多个工具按 for 循环逐个 await；外层多 Worker 并行与此不同。当前调用约束失败只警告，不能视为执行门禁。
4. **回填结果并继续**：把工具结果转换为匹配 tool_call_id 的 tool 消息，追加到本次运行的 messages，再向模型请求下一轮决策。工具返回 success=False 也可能被作为观察结果交给模型，不自动代表整轮失败。
5. **正常收尾**：模型不再返回 tool_calls 时，把文本当作最终回答；进行现有输出检查和可选修补、Worker 后处理，然后返回 answer、iterations、agent_id。这个停止条件仅说明模型停止请求工具，不证明回答正确、任务覆盖或业务动作成功。
6. **预算与异常收尾**：三个 Worker 默认主循环上限为 5 轮；AgentLoop 类默认值为 10，但不是这些 Worker 的默认实际配置。工具默认预算为 2 次，当前只做批前检查，可批内超额；耗尽时仍继续带工具请求并用提示要求作答。正常耗尽主循环后，会额外调用一次禁用工具的模型做总结，因此 5 轮不等于最多 5 次模型请求。若最后一轮异常标记 failed，State.is_completed 也将 failed 视为终态，跳过耗尽总结且可能返回空字典；耗尽后的总结失败则返回错误文案，却标为 completed。

仅用于理解的假设轨迹：研究任务 → 模型请求 search_knowledge → 本地程序执行并返回资料 → 模型判断是否还需另一工具 → 资料足够时生成回答。具体调用次数和选择由模型决定，可能直接回答；这不是已运行验证的案例，也不保证必然检索或提高准确率。

## 工具参数与最终输出约束

核对日期：2026-10-13。只读核查 `agents/skill_registry_mixin.py`、`core/skill_registry.py`、`core/llm_client.py`、`.claude/skills/search-knowledge/script/search.py`、三个 Worker 的提示与后处理、`constraints/validator.py`、`validation/auto_fixer.py` 和 Lead 的 JSON 解析。未导入或运行这些模块，未调用模型或检索。

ReAct 在本项目指“模型判断下一步 → 请求工具 → 程序执行 → 观察结果 → 再判断”的循环。Lead 的任务规划在外层；Worker 的 Loop 不要求每次先输出完整计划，也允许第一轮直接回答。

### 参数如何形成并执行

1. 开发者写 Skill 函数及参数，例如 `search_knowledge(query: str, max_results: int = 5)`。
2. 自动发现 Skill 后，Mixin 使用 inspect.signature 获取参数名称，并以有没有默认值判断必填。工具总体描述来自 SKILL.md 的 YAML frontmatter；参数说明只是名称转成标题。
3. 当前自动类型推断没有使用 Python 类型注解：名称含 count/limit/max/iterations 的参数定义为 number，其余定义为 string。于是 max_results 被声明为 number，而非函数注解中的整数；Python 默认值没有加入工具 Schema。
4. Registry 把这些定义转换为 tools 的 JSON Schema properties/required，随消息发给模型；当前生成定义未设置 strict 或 additionalProperties=False。
5. 模型根据问题与反馈生成参数值。Client 对 arguments 做 json.loads，Agent 将解析值以 **arguments 交给注册表，注册表调用实际函数；省略可选参数时由 Python 函数使用默认值。没有统一的执行前字段、类型、范围或业务语义校验，类型注解本身不执行验证。
6. 不合法 JSON 在解析阶段抛异常；缺参数或多余参数等可能直到函数绑定/执行才失败，并由注册表包装为 success=False。能解析 JSON 不代表字段正确，更不代表有执行权限。

| Lead 任务计划 | 提示要求 JSON，正则提取，再 json.loads | 无统一 Schema 与任务语义校验，详见 FLOW-02 |
| 模型工具参数 | tools 提供参数结构；返回 arguments 经 json.loads 后执行 | 无统一执行前类型、范围、额外字段和授权门禁，详见 TOOL-01/02 |
| Worker 最终回答 | 提示要求文本段落；YAML 驱动部分关键词/长度/正则检查，修补部分提示语；Worker 再提取字段 | 不是严格 JSON 输出校验；违规不一定拦截，且并非全部出口覆盖 |

Consultation 的段落要求为【回答】【核心建议】【免责声明】，后处理通过正则提取建议和免责声明。Diagnostic 通过文本关键词推断风险；Research 识别 A/B/C 级文本、统计“文献”一词次数，并固定赋 evidence_provided=True，不能证明实际来源存在或证据等级正确。AutoFixer 主分派只接入添加免责声明和风险提醒；有其他修复函数不代表它们被执行。

程序把回答装进 answer/iterations/agent_id 等字典，以及工具结果做 json.dumps，是序列化和包装，不等于模型的回答通过了 JSON Schema 校验。输出检查失败在主路径中记录警告并尝试有限修补，不能解释为不合格结果全部被拒绝。

| 编号 | 新记录/细化的改进项 | 候选处理办法与验收 |
|---|---|---|
| TOOL-03 | 自动参数契约忽略注解和默认值，按名称猜类型，缺少边界和额外字段检查 | 为可信工具定义明确参数模型；执行前验证必填、整数/布尔/数组等类型、范围和额外字段；非法参数零执行，可选参数缺省行为明确。JSON 可解析、字段有效、语义正确与有权限分别验证 |
| OUTPUT-04 | 文本关键词和正则提取不等于结构/事实校验；Research 固定证据标志及词频统计容易误导 | 按任务定义输出字段契约；证据标志和来源数从可追溯工具结果计算，缺失保留 unknown/null；模型字段校验与实际证据核查分别进行 |

后续方向：模型按明确结构生成 → 程序进行字段与业务校验 → 无效时有界修正或返回失败 → 对写入另行校验身份、确认与幂等 → 将已验证数据渲染给用户。框架或模型的结构化输出能力只能辅助格式约束，不能替代业务、证据和权限校验。当前仅记录，未实施。

## 本地医学知识库与网络搜索的位置

核对日期：2026-10-13。只读核查 `knowledge/milvus_kb.py`、`knowledge/scripts/import_hardcoded_data.py`、`research/web_search.py`、`research/deep_research_workflow.py`、`research/evidence_synthesizer.py` 及 deep-research Skill。没有打开数据库、加载模型、执行导入、联网搜索或调用模型。

### Milvus 保存什么

Milvus 是通用向量数据库组件，医学内容来自项目提供的文档，不是数据库自带的医疗知识。当前默认使用本地 Milvus Lite 文件 `knowledge/data/milvus_lite.db`，集合 medical_knowledge，嵌入模型默认 BAAI/bge-small-zh-v1.5。`knowledge/data/documents/` 文件清单共 10 个 TXT，涵盖生活方式、症状、ICD-10 和指南类材料；这不是已导入条目数，也不能证明文本来自经核验的官方原文。

构建链路是“整理 TXT → 导入脚本读取内容和生成元数据 → 切分文本 → Embedding 转向量 → 保存向量、原文片段与元数据”。使用链路是“查询转向量 → Milvus 查找相关片段 → 工具格式化结果 → 模型基于返回资料作答”，属于知识库检索增强。当前为 dense 检索，没有主链路 BM25 混合检索证据。

该医学知识库提供领域资料；Mem0 保存跨会话筛选记忆；未来会话 SQL 保存用户和会话消息；未来业务数据库保存真实登记记录，不能互相混同。

### 网络搜索怎样接入 ReAct

三个 Worker 的技能注册包含 deep_research；模型可在外层 AgentLoop 请求该工具。Skill 内部创建 DeepResearchWorkflow，调用 run：模型生成最多 3 个检索子查询 → 编排网络搜索及 Milvus 查询 → 将结果交给模型做证据综合 → 格式化报告回到外层 Loop。网络搜索是 ReAct 的一次工具调用内的步骤，内部是明确编排的工作流，不是外层模型逐个自由选择每一次网页搜索操作。

WebSearchTool 通过 DDGS 库调用 text 搜索，代码依次尝试 bing、duckduckgo、auto 后端，取得标题、URL 和摘要。该顺序是静态代码事实，实际 SDK 支持、可用后端和联网成功未验证。DeepResearch 主路径使用 search，不调用已有 fetch_content/search_with_content，所以不能将搜索摘要描述为已经阅读全文或核实原始论文。医学域名过滤函数存在，但没有在该主路径启用。

主路径未将网络结果自动写入 Milvus。DeepResearch 的 max_iterations 参数实际上用于计算搜索结果额度，再调用一次 workflow.run；另有 research_with_refinement 方法，但该 Skill 没有调用它。工具内部的模型请求、网页请求和查询次数可能多于外层一次工具计数，必须分别预算。

| 编号 | 本块新增的改进项 | 候选处理办法与验收 |
|---|---|---|
| RETRIEVAL-03 | 分块长文本到末尾后仍将 start 设为 end-overlap，默认 overlap>0 时可能重复末尾片段，不能终止；这是静态发现，未运行复现 | 实施时先离线复现，再增加到末尾终止和参数校验；短文、长文及非法 overlap 均能有界完成，末尾不反复添加 |
| RETRIEVAL-04 | 导入元数据的 source 多为按文件类型生成的通用标签，缺少可靠原始出处、版本及审核状态 | 保存原文来源、日期/版本、稳定文档 ID 和审核状态；未核验材料明确标识；来源不会在工具格式化和最终引用中丢失。与 RETRIEVAL-02 联动 |
| RESEARCH-01 | max_iterations 名称与实际搜索额度含义不符；单次工具内部含额外模型/搜索请求 | 区分外层 Loop 轮次、子查询数、结果条数、内部模型和时间预算；前端和 trace 反映真实调用量，未接入细化循环不声称多轮研究 |
| RESEARCH-02 | 网络主路径未启用域名过滤、主要使用摘要；同步 DDGS 与 Milvus 工作在 async 流程内可能阻塞；搜索错误可变为空结果 | 按任务选择来源范围与必要正文获取，正确核验 URL 主机；阻塞操作放入受控执行器，保留失败/无命中/部分成功状态；报告与实际证据覆盖一致，不能把模型自报置信度当正确率 |
